# Browser theming: Helium and other Chromium browsers

Research and live tests from 2026-11-09, on Helium 0.21.1.1 (Chromium 157.0.8103.38) and macOS build Darwin 27.2. Nothing here is built into Scene yet. The tools are in `Scripts/browser-theming/`.

## Summary

- **Dark themes work live.** A forced `BrowserThemeColor` policy, seeded with the theme background, recolors a running Helium in about 6 seconds with no relaunch. Flexoki Dark `#100F0F` gave a `#141212` frame.
- **Light themes cannot be both live and even.** The policy theme always draws a tinted frame, a white toolbar and a grey address bar. Removing the policy to get Helium's own Material look only takes effect at the next launch.
- **Open decision for the user:** how light themes behave (see [Light themes](#light-themes)).

## Two ways Chromium themes itself

| | Policy color (`BrowserThemeColor`) | Material user color (profile prefs) |
|---|---|---|
| Where | Forced managed preference | `browser.theme.user_color2` and `color_variant2` in each profile's `Preferences`, with `extensions.theme.id = user_color_theme_id` |
| Theme type | Autogenerated theme (`custom_theme` is set) | Material dynamic color |
| Helium styling | Skipped. Helium's patch says "Custom themes retain their frame colors because they skip these overrides". | Applied. In light mode the frame and toolbar are both Neutral T98. |
| Fidelity | Dark: frame equals the seed. Light: see below. | Fixed tones. Light: Neutral T98. Dark: Secondary T12 frame. |
| Live | Yes, with the steps below | No. A running browser rewrites `Preferences` on exit. |
| Needs root | Yes | No |

Omarchy uses the policy route on Linux: `{"BrowserThemeColor": "<hex>", "BrowserColorScheme": "device"}` in each browser's managed policy directory, then `--refresh-platform-policy`. The seed is the theme's `chromium.theme` (an RGB triple), default `#1c2027`. Light themes have hand-picked seeds there, for example Flexoki Light `242,240,229` rather than its background `#FFFCF0`.

## Live policy on macOS

Chromium's macOS loader (`components/policy/core/common/policy_loader_mac.mm`) watches `/Library/Managed Preferences/<user>/<bundle-id>.plist` and reloads about 5 seconds after it changes. It reads the values with `CFPreferencesAppValueIsForced`, so they count as mandatory.

Writing that file is not enough. cfprefsd and every running process cache managed preferences, and nothing tells them the file changed. The sequence that works:

1. As root, write the plist directly (`NSDictionary.write(toFile:)` or PlistBuddy, mode 0644).
2. As root, call CoreFoundation's private `_CFPreferencesManagementStatusChangedForDomains(CFArray of domains)`. This is what macOS's managed-settings service calls after a change. It flushes managed sources and posts `com.apple.MCX._managementStatusChangedForDomains` and `com.apple.CFPreferences._domainsChangedExternally`.

Chromium's file watcher then reloads on its own. `--refresh-platform-policy` is not needed, though it works: a second launch hands it to the running browser.

`Scripts/browser-theming/managed-policy-write.swift` does both steps. An empty value removes the key, and it deletes the file once the file has no keys left.

Bundle ids that read the same file: `net.imput.helium`, `com.google.Chrome`, `com.brave.Browser`, `com.microsoft.edgemac`, `org.chromium.Chromium`. Only Helium is tested.

### What did not work

- `sudo defaults write "/Library/Managed Preferences/gf/net.imput.helium" …` reported success but wrote no file.
- Posting the MCX distributed notification or the Darwin notifications from an unprivileged process changed nothing.
- `killall cfprefsd` refreshed new processes but not running ones, Helium included. Killing cfprefsd also seemed to break later invalidation for processes started before the kill.
- `_CFPreferencesWriteManagedDomain` from a root process returned false. cfprefsd probably requires a private entitlement.

## Light themes

`GetAutogeneratedThemeColors` (`chrome/common/themes/autogenerated_theme_util.cc`) darkens the frame until the toolbar, which is lighter, contrasts with it by at least 1.3:1. It then lightens the toolbar towards a 1.6:1 contrast, stopping before white only for darker frames. `Scripts/browser-theming/autogenerated-theme.py` models this and matches the screenshots:

| Seed | Frame | Toolbar | Seen in Helium |
|---|---|---|---|
| `#FFFCF0` (Flexoki Light background) | `#FFDE5A` saturated yellow | `#FFFFFF` | Frame `#FBE383` |
| `#F2F0E5` (Omarchy's Flexoki Light seed) | `#E3DEC7` | `#FFFFFF` | Frame `#E8E4D3`, toolbar white, address bar `#E7E7E8` |
| `#D4CEAA` | `#D4CEAA` | `#EEECDE` | not tested |
| `#100F0F` (Flexoki Dark background) | `#100F0F` | `#3B3636` | Frame `#141212` |

A light frame always gets a pure white toolbar. A tinted toolbar needs a darker khaki frame. The address bar stays a neutral grey for any custom theme.

Removing the policy does not bring Helium's Material look back live. `ThemeService::HandlePolicyColorUpdate` calls `InitFromPrefs`, which returns early for `user_color_theme_id` without swapping out the policy theme or notifying the UI. Tested: the policy key was removed and macOS reported it gone, but Helium kept the policy theme.

The options:

| Option | Look | Live |
|---|---|---|
| A. Policy with a tuned light seed | Tinted frame, white toolbar, grey address bar | Yes |
| B. Material user color in `Preferences`, no policy | Even, tinted near-white (Neutral T98) | No, needs a relaunch |
| C. Policy with a darker seed such as `#D4CEAA` | Tinted toolbar, darker frame | Yes |

The suggestion so far: dark themes use the policy, and light themes use B with an automatic relaunch, unless live matters more.

## Material route numbers

Measured on the 86 variants of Scene's bundled themes. ΔE is CIE76 between Helium's chrome color and the theme background.

| Mode | Best fixed rule | Median ΔE |
|---|---|---|
| Light | seed = background, Tonal Spot (`color_variant2 = 1`) | 3.8 |
| Dark | seed = background, Neutral (`color_variant2 = 2`) | 9.1 |

Even the best choice per theme only reaches a median of 7.0 in dark, because the tone is fixed at T12 and most Scene backgrounds sit at T2–T9. Near-black greys have no stable hue, so seeding with them gives a random tint (matte-black turns teal). `color_variant2`: 0 system, 1 Tonal Spot, 2 Neutral, 3 Vibrant, 4 Expressive.

## Helium specifics

- Layout is `helium.browser.layout` in each profile (0 Classic, 1 Dynamic, and so on). Classic shows the frame as a separate tab strip.
- Helium does not restore tabs by default (`session.restore_on_startup` unset). A relaunch step must not lose the user's tabs. This is untested.
- Helium updates itself with Sparkle.

## Open questions

- Does the Screen Time configuration profile, which manages `/Library/Managed Preferences/<user>`, rewrite or remove Scene's plist? It rewrote `complete.plist` at 10:04 on the test day.
- How Scene gets root for the write: a privileged helper installed once (`SMAppService` daemon) or an admin prompt per switch. Omarchy uses a passwordless sudoers rule.
- `_CFPreferencesManagementStatusChangedForDomains` is private API. It belongs with the other private calls, gated on tested macOS builds.
- Chrome, Brave and Edge are untested.

## Tools

| File | What it does |
|---|---|
| `managed-policy-write.swift` | `sudo managed-policy-write <user> <bundle-id> <key> <value>`: writes the managed plist and sends the change notice. An empty value removes the key. |
| `managed-policy-probe.swift` | Prints the forced `BrowserThemeColor` for `net.imput.helium` whenever it changes, to check whether a running process sees a write |
| `autogenerated-theme.py` | Frame and toolbar a policy seed produces |
| `material_roles.py` | Material header, toolbar and omnibox colors for a seed, per variant (needs `pip install materialyoucolor`) |
| `material-vs-themes.py`, `material-best-seed.py` | The Material numbers above, run against `Themes/` |

Build the Swift tools with `swiftc -O <file>.swift -o <name>` (set `DEVELOPER_DIR` as usual). To undo a test: `sudo rm "/Library/Managed Preferences/<user>/net.imput.helium.plist"`.
